## 0. 整体结论（二值）

**确定根因**：

三方PC"找到手机里的文件"不返回结果卡的根因在**手机侧跨端文件搜索结果卡片回传链路失效**——在本次分析覆盖的全部搜索运行中（8.12 复现时段 19:32-20:11 的 12 个搜索会话 + 8.13 复现），手机 agent 从未把搜索结果以文件卡片部件（`miclawFile` parts）交付回 PC：8.12 logcat 可见的 12 次子任务完成事件 + 8.13 1 次（共 **13 次）完成时均 `extraParts=0`**（另有 8.12 109cdb80 任务手机侧日志未入缓冲、PC 侧确认为同型失败），PC 端收到的 12 个 artifact 均无 miclawFile 部件（main.log 全文 miclawFile 命中 0），只收到纯文本（文件名称），`buildRichContentFromArtifactParts` 因无 `miclawFile` parts 不生成 `file_cards`，故无法渲染结果卡。链路失效由两个缺陷叠加：

- **缺陷 1（8.12 构建，确定性，已修复）— 回环抑制误拦截合法文件回传**：`DeviceLoopGuardHook`（为阻断 file_arrival 回环引入，f0128710a3）在 `messageSource=group_task` 上下文对 `cli device send --preview-only` 内容级拦截（11 次实证），与交付契约提示词（"搜索类任务必须 device send --preview-only 交付"）自相矛盾——LLM 忠实执行契约必被拦截，回退为纯文本。这正是 exReasonAnalysis 所写"回环抑制影响了文件回传"。修复 `bd7e7cb087`（8.12 21:16，已进 main + release/os4.0.1-v8.1）。
- **缺陷 2（8.12+8.13 构建，非确定性，仍存在）— LLM 不执行交付契约**：mimo 模型对交付工具（device send / remote_file）的调用不稳定，多数运行（含 8.12 20:11 主复现、8.13 全部复现）根本不调用交付工具，直接输出文本文件清单。8.13 临时包（交付指引已改为 remote_file，4c05afca37 分支）验证仍复现，即缺陷 2 未解决。

**后续动作**：无需补日志（证据链完整闭合）。缺陷 2 需要确定性兜底修复（见第 8 节），并需回归验证当前 main（含 bd7e7cb087）在真实链路上的表现。

## 7. 根因定位（证据链 + 闭合性验证）

**证据链：现象 → 直接原因 → 深层原因 → 根因**

1. 现象：PC 互传 tab 点击"找到手机里的文件"→ 不返回结果卡（8.12）/ 返回文件名称而非结果卡（8.13）。
2. 直接原因：手机侧 agent 搜索结果以纯文本回传，未携带文件卡片部件；13 次 subtask 完成全部 `extraParts=0`（logcat 1198727/480606 等）；PC `buildRichContentFromArtifactParts` 无 miclawFile parts 不生成 file_cards（deviceChatApi.ts:174-186），UI 无卡片（CardRenderer.tsx:25）。
3. 深层原因（双缺陷）：
   - 缺陷 1：回环抑制误拦截——8.12 构建 DeviceLoopGuardHook 在 group_task 上下文内容级拦截 `device send --preview-only`（11 次 Blocked 实证，logcat 599122-1161081；源码 DeviceLoopGuardHook.kt:232-243），与交付契约（DeviceAgentBridge.kt:632-651）矛盾；LLM 忠实执行即被拦 → 回退文本。修复提交 bd7e7cb087 根因说明原文："f0128710a3 (08-11) 为阻断 file_arrival 回环引入 cli 内容级拦截时，把 device send（文件回传）与 device task（任务派发）同等对待、未按消息源区分"。
   - 缺陷 2：LLM 不执行交付契约——mimo 模型多数运行不调用 device send/remote_file，直接输出文本清单（8.12 20:11 主复现 logcat:1197269-1197301 推理说"应 preview-only 交付"却输出文本；8.13 复现 logcat 无任何 remote_file 调用）。8.13 临时包（已修复缺陷 1 形态）仍复现即缺陷 2 所致。
4. 根因：手机侧跨端文件搜索结果卡片回传链路不可靠——"回环抑制"误拦截合法回传（确定性缺陷，已修复）+ LLM 对交付契约执行不稳定（非确定性缺陷，未修复）叠加，导致搜索结果永远无法以文件卡片回传 PC，PC 无法渲染结果卡。

**闭合性验证**：每步双证据（日志+源码）；无逻辑跳跃；能解释全部观察（13 次失败、11 次拦截、8.13 修复后仍复现、17:43 照片流成功对照）；闭环表无 ❌。

**内部置信度标注（不进定谳）**：缺陷 1 实证；缺陷 2 实证（行为层面，LLM 内部决策机制为推断）；8.13 临时包是否含 bd7e7cb087 修复为推断（apk 构建 provenance 不可直接验证，但 8.13 提示词形态=4c05afca37 分支，晚于 bd7e7cb087，且 8.13 无拦截记录）。

## 8. 修复方案（2.9：绑定根因 + 修复机制 + 分层 + 验证方法）

### 止血方案（缺陷 1，已完成合入，需确认发布）
- **F1（绑定缺陷 1）**：DeviceLoopGuardHook 对 worker（group_task/device_a2a）场景放行 `device send --scope cloud --to <发起端> --preview-only`，仅 file_arrival 展示轮拦截。修复机制：bd7e7cb087（8.12 21:16）已实现 + 白名单加固（90ecc5e93e）已进 main 与 release/os4.0.1-v8.1（cherry-pick 0e8ddeded0）。**待办**：确认 OS4.0 分支发布状态（exNextPlan 提到审批进 OS4.0）；验证方法：复现原场景 → device send 不再被拦截、卡片可回传。

### 长线方案（缺陷 2，核心未修复项）
- **F2（绑定缺陷 2）**：为搜索类 group_task 交付增加**确定性兜底**，不依赖 LLM 自觉调用交付工具。修复机制（候选，择一或组合）：
  - F2a：手机侧在 `completeSubtask` 前对搜索结果做结构化后处理——当 agent 文本结果中含文件路径清单（或已有 `Part.Data(action=miclaw.file.search)` 数据部件）时，由系统（非 LLM）将文件转换为 `miclawFile` parts 注入 artifact（对应 GroupTaskReceiver.completeSubtask / SubtaskState.miclawFiles），保证 extraParts>0；
  - F2b：交付工具首类化——将 `remote_file`/`device send` 提升为 group_task 场景 preload 工具（当前"不在 preload 工具列表，须经 cli 调用"是 LLM 不调用的一大诱因，见 8.13 提示词原文），降低模型调用门槛；
  - F2c：模型侧约束——提示词强化"输出文本清单=任务失败，必须调用交付工具"，并对"仅文本、零交付"的搜索结果类任务在完成后端校验重试（一次）。
  - 预期行为变化：搜索类任务无论 LLM 是否自觉，结果都能以文件卡片回传 PC。
- **F3（验证闭环）**：需在真实链路回归"找到手机里的文件"→ PC 显示结果卡并可下载（验证方法：复现原场景 → 修复后 PC 返回结果卡且可点击下载；同时回归 17:43 照片流不受影响）。
