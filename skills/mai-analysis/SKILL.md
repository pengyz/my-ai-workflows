# IPD 根因分析 + 结论上传

分析问题单并给出**可被修复工作流直接使用的完整结论**。核心原则：

1. **必须基于日志定位根因**，所有结论有日志+代码证据支撑，不凭描述猜测
2. **日志全量分析**，不只关注问题现象：一份日志可能多个问题、多个根因
3. **根因定谳必须结合源码分析（强制）**：任何根因结论必须把流程中涉及到的**全部源码**（端侧/对端/协议/工具/桥接，两端都要）逐一分析验证后才可定责；**只闭合日志证据链、不经过源码深入分析得出的根因视作无效，禁止上传**。若分析者不确定相关源码的仓库路径/模块/分支/版本，**必须停下来向用户询问确认，不得凭猜测假设源码位置**；无法确认源码时，结论只能标注"无法给出结论（待源码确认）"，不得定谳
4. **根因定因必须深度分析**：每个定责环节深挖到"为什么"（代码逻辑+运行时行为+触发条件），输出端到端执行时间线，结论**整体二值化**（确定根因 / 无法给出结论），**禁止"可能/疑似/大概率"等模糊定责、禁止"A 环节确定 B 环节待补"的混合定谳**
5. **关键结论必须经子 agent 独立审查**：四道门禁 A1/A2/A3/A4（流水线，A1 与 A2 并行 → A3 串行在 A1 后 → A4 串行收尾），**通过绑定结论版本**，全部通过才可上传结论
6. 审查不过 → 打回重做对应阶段（任意门禁可打回任意前置门禁/步骤，连续互打升级用户仲裁）；用户可显式豁免（记录豁免原因）
7. **结论必须可证实**：主报告与每份门禁报告附**凭证清单**（实际读取的 file:line + 原文摘录 + 执行操作），门禁随机抽查重放，引用与实际不符按分级处置（见 3.2），凭空捏造 = 伪造 → 打回

## 触发方式

- "分析 IPD 问题 ISS-xxx"
- "根因分析 ISS-xxx"
- "/mai-analysis ISS-xxx"

## 前置

环境门禁（复用 `mai-env-doctor` / `setup.py`）：`mi-adt` MCP 可用（查询/评论）、**2.4 涉及的全部源码仓库**可用（osbot / miclaw_desktop / ContinuationApp 等，缺哪个在 2.4 ① 向用户确认该仓库路径）。MCP 参数细节见 `ipd-mcp-setup` skill（appAccount/issueId/issId）。

## 工作流程

### Step 1: 获取 IPD 问题信息

调用 `mi-adt` `M_issueQuery`（filters: issId EQ），提取：issueTitle / issueDescription / issuePriority / issueStatus / issueAssigneeId / exHandleAction / issueTestComponent / attachmentJson。

同时拉取问题单**全部评论**（`M_pageOverallComment` / `M_getCommentList`）——供 Step 3 门禁 A3 核查。

**1.0 已有定性结论检查（LLM 判定，有则跳过分析）**：

阅读该单**全部信息**——issueDescription、全部评论、exReasonAnalysis、exNextPlan、rootCause、issueRootReason、changeId——由 **LLM 综合判定**是否已有**有效**的根因定性结论：

| 判定 | 依据 |
|------|------|
| ✅ 已有有效定性 | 明确根因 + 有证据/分析支撑 + **未被推翻**（无 QA 质疑/无重新打开/无反驳评论） |
| ❌ 无定性 | 无任何根因分析 |
| ❌ 定性无效 | QA 已推翻 / 评论质疑 / 被后续讨论否定 / 只有猜测无证据 / 结论存疑待定 |

> 注意：字段有值 ≠ 有效。用户不一定按规则更新（exReasonAnalysis 可能为空或模糊），且即使有根因，QA 可能已推翻——**必须 LLM 读评论判断"当前是否仍成立"**，不能机械匹配字段。

**判定 ✅ 已有有效定性 → 不分析**：
- 展示已有定性结论内容给用户
- 返回该单的 **IPD 链接**（`https://ipd.mioffice.cn/.../item/<id>`）供用户确认
- **跳过后续分析/审查/上传**，标记状态 `skip: 已有有效结论`
- 若用户仍要求重新分析（对结论存疑），才进入 Step 2

**判定 ❌（无定性 / 定性无效）→ 继续分析**，进入 Step 2。

**1.1 查询修复数据库状态**（定位 WF_ROOT 见环境门禁）：
```bash
python <WF_ROOT>/fix-db.py query <issId>
```
- 已有记录（analyzing/conclusion_uploaded/fixing/mr_created/merged）→ 展示历史状态,若已有结论则提示用户是否重复分析;若已 merged/closed 提示问题可能已修复
- 无记录 → 登记本次分析（拿到 issueTitle 后）：
  ```bash
  python <WF_ROOT>/fix-db.py add <issId> --title "<issueTitle>" --status analyzing
  ```

展示给用户确认。

### Step 2: 日志下载与全量分析

**2.1 下载附件**：从 `attachmentJson` 提取所有 fdsId，下载全部日志/截图到工作目录（`/tmp/ipd-<issId>/`），解压 zip。

**2.2 日志全量扫描**：

① **时间范围确认**：日志起止时间是否覆盖问题发生时段（不覆盖则标记，按 2.8 用户决策流程处理）
② **关键事件提取**：搜索所有相关事件（不只问题现象）——用户交互、系统状态变化、错误异常、性能指标、业务逻辑（tool call/agent decision/search/transfer）
③ **完整时间线**：按时间顺序排列所有关键事件 `HH:MM:SS.mmm [Component] 事件 [file:line]`
④ **Session/Query 统计**：多少个 session、每个 session 多少个 query、各自结果（成功/失败/超时）
⑤ **问题现象定位**：在时间线中标记 QA 反馈的问题点
⑥ **成功/失败样本对比**：同一份日志中是否有成功类似操作？对比差异
⑦ **异常模式识别**：频繁重试、异常延迟、资源耗尽、状态不一致、消息丢失

**2.2b Android logcat（adb logcat / "284 日志"）分析与日志完备性检查（强制）**：

> Android 端问题**必须**分析系统级 adb logcat（测试要求抓的"284 日志"通常即此）。**仅分析 app 级 debug_log（如 voiceassist 日志）不等于分析了 logcat**——worker/agent 的真实执行、服务进程启动、工具调用、binder 调用、系统调度都只在 logcat 中可见。

**分析前日志完备性检查（前置门禁）**：
- 分析开始前先检查附件中日志的**完备性**：是否包含系统级 adb logcat（bugreport 内层 dumpstate zip 的 `bugreport-*.txt` 主缓冲）？logcat 是否覆盖问题时段？
- **必须包含 logcat**：Android 端问题若无 logcat（或 logcat 未覆盖问题时段），**Android 端执行链路无法完整闭合**——在报告显著位置给出**警告**（"⚠️ 日志完备性警告：附件缺少系统级 logcat / logcat 未覆盖问题时段，Android 端执行链路无法完整闭合"）
- **警告是提醒项，但缺失的闭合后果是硬约束（完整语义链）**：
  1. 分析**不因缺 logcat 而停止**——仍继续分析可用日志/源码，给出当前证据下的最佳结论（含 2.8 决策路径）；
  2. **受 logcat 缺失影响的 Android 执行环节必须作为独立环节写入 2.7 闭环对照表并标 ❌**（不得通过省略该环节规避 ❌）；
  3. 闭环表存在 ❌ → **整体结论必须为"无法给出结论"**（2.5/2.7 硬约束），除非该环节**不参与定责**且有 logcat 之外的直接反证（如 app 级日志 + 源码已完整证明该环节未触发）；
  4. 即：**警告不构成"结论失败"（不停止分析），但 logcat 缺失导致的环节未闭合必然触发"整体降级"**——不允许"带警告仍维持确定根因"（门禁按 3.2/3.3"降级正确性校验"核查）

**Android logcat 关键日志的可能位置**（按优先级查找，具体搜索模式由分析者基于任务与场景自行确定，不在本 skill 预设）：

1. **bugreport 内层 dumpstate zip**：外层 bugreport zip 解压后，常有一个嵌套的 `bugreport-<device>-<build>-<timestamp>.zip`，其内包含 **`bugreport-<device>-<build>-<timestamp>.txt`（通常 100MB+）——即完整 adb logcat 主缓冲（main/system/events 合并）**。这是 Android 端问题分析的**首要日志源**，必须解压并搜索问题时段。
2. **系统级进程日志**（logcat 内的关键服务，具体到组件名称由分析者按任务判断）：
   - AI 搜索/检索类服务进程（如 `com.xiaomi.aicr` 的 search/clip/bert 相关子进程、`com.xiaomi.aiservice`）——搜索/检索类问题的核心执行证据
   - 相册/媒体检索进程（如 `com.miui.gallery` 及插件）
   - 超级小爱主进程（如 `com.miui.voiceassist`）
   - 互联服务（如 `com.xiaomi.mi_connect_service`，app_log 与 continuity 日志）
   - `ActivityManager` / `SmartPower` / `am_proc_start` / `am_proc_bound`：进程启动/调度（证明某能力是否被触发）
3. **app 级 debug_log**（如 `com.miui.voiceassist/cache/debug_log/*.log`、`com.xiaomi.mi_connect_service/release_log/*`）——作为 logcat 的补充，不能替代

**强制要求**：
- 必须定位并解压 bugreport 内层 dumpstate zip 中的 `bugreport-*.txt`（logcat 主缓冲），在问题时段搜索与本任务相关的关键进程/事件（搜索词由分析者基于任务与场景自行确定）
- 分析报告必须列出**实际使用过的 logcat 文件路径 + 行号 + 原文摘录**（凭证清单必须包含 logcat 条目）
- 成功/失败样本对比**必须**包含 logcat 证据
- **未分析 logcat：报告不得进入门禁；门禁核查发现 logcat 未使用或使用率不足 → 整体打回**（见 3.3 A2 强制项；A1 侧按降级正确性校验）

**2.3 问题定界（多端日志交叉验证）**：
- Android 端 / PC(Mac) 端 / 网络中间层逐端检查（请求发出？参数正确？响应收到？错误处理触发？）
- 定界结论模板：主责（明确的端）+ 多端证据链 + 次责/协同问题
- **问题域划分**：按 4.6 规则，把识别出的问题划分为主问题/强相关/次生/无关，标注贡献度（高/中/低/无关）——**高贡献问题必须深挖分析，低/无关问题归"其他问题"仅评估影响，防过度发散**

**2.4 源码分析（强制，根因定谳的前置条件）**：

> 本步骤不可跳过。**任何根因定性（含主责/次责/协同、直接原因/深层原因/根因）都必须以源码分析为最终依据**；仅凭日志时序推断出的"某端该做什么却没做/做错"不构成定责。

① **定位源码**：先确认涉及模块在哪个仓库（osbot / miclaw_desktop / ContinuationApp 等）、哪个分支、哪个版本（与问题单/日志版本对应）。**不确定仓库路径、模块、分支或版本时，必须向用户询问确认，禁止自行假设**；用户无法确认时按 2.8 路径 D 处置。
② **全链路源码遍历**：把问题涉及的双端流程逐环节在源码中走通——
   - 发起端：用户 query 如何被 LLM 解析 → 工具调用参数如何构造（instruction/contextHint/agentInstruction）→ 如何写入协议载荷 → 如何发送
   - 传输层：协议消息结构、metadata 字段、通道选择、超时/重试
   - 接收端：载荷如何提取（哪个字段进 LLM prompt）→ LLM prompt 如何拼接 → 工具如何执行 → 结果如何回传
   - 两端都要分析，**不得只分析一侧就定责**
③ **逐文件记录**：每个环节给出 `源码文件:行号` + 关键代码摘录 + 该环节在日志中的对应证据（`日志文件:行号`），形成"代码↔日志"一一对应表
④ **核对版本一致性**：日志中体现的行为（字段名、协议结构、超时时长、错误文案）必须与对应版本源码一致；不一致时标记"版本不匹配，需确认分支"
⑤ **源码无法闭合的环节**：如手机端 worker 执行日志缺失导致无法确认某环节，明确标注"该环节源码已分析但运行时行为缺日志证据"，按 2.8 用户决策流程处理，**不得把未验证的推断当作结论**

**2.5 根因定位（证据链闭合，整体性结论）**：

> **执行顺序**：必须先完成 2.7 闭环复核（产出闭环对照表），再产出本节的整体结论。本节结论以 2.7 闭环表为最终依据。

- **整体性结论强制（核心）**：本分析只产出**一个整体结论**——要么"**确定根因**"（整个证据链完整闭合、无任何影响定责的不明确处），要么"**无法给出结论**"（存在任一未闭合/矛盾/缺证据环节）。**禁止"部分确定 + 部分无法"的混合定谳**：任何关键环节未闭合，整体即降级为"无法给出结论"，不允许用"A 环节确定、B 环节待补"的方式部分定谳上传
> **二值化作用域（与 4.6 衔接）**：整体二值化只针对**主问题与强相关问题**；贡献度**低/无关**的"其他问题"单独列出并评估影响，**不阻塞**整体定谳——但不得把未闭合/未深挖的主问题或强相关环节塞入"其他问题"以回避降级（门禁按 4.6⑥"无关分类抽查"核查）。
- **终止判据（防止无限深挖）**：深挖"为什么"终止于"触发条件可被（代码分支 + 日志分支结果）直接解释，且**再深一层不再改变定责结论**"；"不明确处"限定为"**影响定责环节的证据粒度**"（不影响定责的细节不构成不明确）。达到终止判据即视为该环节深挖充分，不得无限追问导致产出率归零
- 证据链结构：现象 → 直接原因 → 深层原因 → 根因,每一跳都要 `日志证据 [file:line] + 代码证据 File.kt:123`（代码证据来自 2.4 的源码分析，缺一不可）
- **结论必须符合 3.1 结论输出规范**：含关键流程描述 + 执行时间线 + 深度分析 + 日志证据 + 源码证据 + 闭环表 + 结论二值化 + 依赖溯源
- **深度分析强制**：每个定责环节必须深挖到"为什么"（代码逻辑 + 运行时行为 + 触发条件），不得停留在现象描述或表面归因（终止判据见上）
- **执行时间线强制**：输出端到端时间线（精确时间戳、双端对应事件、各环节耗时），时间线必须与日志原文逐点一致、覆盖问题全过程
- **结论二值化强制**：整体判定只能是"确定根因"（证据链完整闭合、无任何影响定责的不明确处）或"无法给出结论"（明确列出全部缺口与后续动作）；**禁止"可能/疑似/大概率"等模糊定责**
- **内部置信度标注（对内可行动，不进定谳）**：分析过程文档/内部报告可标注各环节置信度（实证/推断/猜测），帮助定位薄弱环节；但**置信度标注严格不进入整体定谳与 IPD 上传**——对外定谳只有二值（确定根因 / 无法给出结论）
- 验证闭合性：每步双重证据、逻辑无跳跃、能解释所有观察到的现象；**并以 2.7 的日志↔源码闭环对照表为最终依据**（闭环表有任何 ❌ 环节 → 整体结论必须为"无法给出结论"）
- **不能给出源码级解释的环节 = 证据链不闭合**，整体结论降级为"无法给出结论"，并按 2.8 处理（用户决策：补日志申请 / 自行复现 / 要求 QA 复现 / 源码待确认）

**2.7 日志证据 + 源码分析逻辑闭环复核（独立步骤，强制）**：

> 本步骤是**独立于日志分析（2.1-2.3）与源码分析（2.4）的第三道自检**，在 2.5 整体结论产出**之前**必须完成（执行顺序：2.4 源码分析 → 2.7 闭环复核 → 2.5 根因定位 → 2.8 决策 → 2.9 修复方案 → 2.10 报告输出）。目的：把"日志里发生的事"和"源码里定义的逻辑"逐环节双向对齐，确保根因结论不是单侧推断而是**日志↔源码双向闭合**。**未完成本步并形成闭环表的分析，不得产出整体结论、不得进入 Step 3 门禁。**

① **正向闭合（日志 → 源码）**：时间线中每一个关键事件/行为（用户 query → 工具调用 → 协议消息 → 对端处理 → 结果回传，逐条），在源码中必须能找到**产生该行为的实现点**（哪个文件哪段逻辑、哪个字段、哪条分支）。找不到源码对应 = 该环节未闭合。
② **反向闭合（源码 → 日志）**：源码中定义的流程分支（工具参数构造、prompt 拼接、超时/重试、错误处理、结果回传），在日志中必须能找到**实际执行痕迹**（对应日志行、字段值、分支结果）。有源码定义但日志无痕迹 = 须解释（未走到该分支？被跳过？被吞掉？），解释不清即未闭合。
③ **输出闭环对照表**（写入分析报告第 6 节）：
   | # | 环节 | 日志证据 file:line | 源码证据 File.kt:line | 双向闭合? | 说明 |
   |---|---|---|---|---|---|
   | 1 | … | … | … | ✅/❌ | … |
   每个环节必须两列都有证据且逻辑一致才标 ✅；任一列缺失或矛盾标 ❌ 并说明缺口。
   **闭环表完整性强制**：Android 端问题的闭环表**必须覆盖 logcat 强制环节**（logcat 中的关键执行/服务进程启动/工具调用/检索/回传等环节逐条入表）；附件缺 logcat 时，受影响的 Android 执行环节必须以独立行入表并标 ❌（见 2.2b）——**不得通过省略 logcat 环节来规避 ❌**。
④ **矛盾处理**：日志行为与源码逻辑矛盾（例如日志显示走了 A 分支但源码条件不满足、字段值与源码定义不符）→ **必须定位矛盾根源**（版本不匹配？条件判定不同？日志截断？）才能继续；无法解决时该环节标记未闭合，整体结论降级为"无法给出结论"。
⑤ **未闭合项的处置**：闭环表存在任何 ❌ 时，**整体结论必须为"无法给出结论"**（不允许部分定谳）；按 2.8 走用户决策流程，不得自行"补拉"或在缺证据下定谳。

**2.8 日志缺失 / 证据无法闭合时的用户决策流程（强制，替代任何"自动补拉"行为）**

> 本 skill **不执行"自动补拉日志"**。证据不足时，按以下四条路径之一走，且必须先向用户汇报、由用户决策：

**路径 A — 申请补日志（日志确属缺失，且复现不可行/成本过高）**：
- 向用户汇报：缺什么日志（哪个端、哪个进程、哪个时段、需要哪些字段/工具调用记录）、为什么缺、缺了之后无法闭合哪些环节
- 用户确认后，**补一条 IPD 评论**写明所需日志清单（供 QA/测试方按清单提供）
- 在结论文件中标注"**无法给出结论，已申请补日志（IPD 评论 <时间>）**"，**不进入定谳上传**

**路径 B — 自行复现抓日志（判定可以自己尝试复现）**：
- 前提评估（必须记录）：能否构造**相同的测试环境**（设备型号/系统版本/软件版本/网络拓扑/账号状态）？**复现概率**如何（高/中/低，依据是什么）？
- 评估可行 → 利用**现存测试能力**尝试复现并自抓有效日志：`mai-osbot-test`（测试编排，按场景路由 eval/smoke 引擎）、`osbot-talk-to-osbot` / `sidekick-talk`（与运行中实例交互、触发行为并抓日志）、`osbot-eval`（场景用例跑通），回到 Step 2 重新分析；**若现存能力无法覆盖该复现场景（无可用复现/抓日志手段）→ 路径 B 自动降级为路径 A 或 C**（不得虚构复现）
- 评估不可行（环境无法构造/复现概率过低）→ 转路径 A 或 C

**路径 C — 要求 QA 复现并提供特定日志（最终无法给出结论时）**：
- 输出**后续待办**：明确要求 QA 按清单复现并提供特定日志（写清复现步骤、需要的日志/抓取方式、期望覆盖的时段）
- 在结论文件中标注"**无法给出结论，后续待办：QA 复现并提供特定日志**"，**不进入定谳上传**
- 若用户决策是自己复现 → 走路径 B，不存在路径 C 的问题（自己抓有效日志）

**路径 D — 源码待确认（仓库路径/分支/版本无法确定）**：
- 向用户确认所需源码的仓库路径/分支/版本，**设时限**（默认 1 个工作日，可在汇报时与用户约定）
- 时限内用户确认 → 继续 2.4 源码分析
- **超时未确认** → 结论标注"**无法给出结论（待源码确认）**" + 待办清单（列明待确认项），**不阻塞流程收尾**、不进入定谳上传

**关键约束**：四条路径都不得在缺证据时产出"确定根因"结论；都必须先向用户汇报并记录用户决策（决策人 + 时间 + 所选路径）。

**2.9 修复方案绑定与复核（强制）**：

① **修复项必须绑定根因**：每个修复方案必须显式绑定到根因证据链的**具体环节**（"修复 X 以解决根因 A 的 contextHint 弱化 → 对应 SendTaskToDeviceTool.kt:492"），不得出现与根因无关或泛泛的修复项。
② **修复机制说明**：每个修复项必须说明**修复机制**——改哪里、为什么这样改能消除该环节的缺陷（对应源码位置 + 逻辑变更 + 预期行为变化）。
③ **修复效果验证方法（分析阶段只写明方法，不执行修复）**：本 skill 只做分析定谳，**不在分析阶段写修复代码或跑修复验证**；每个修复项写明验证方法（复现原场景 → 修复后不再复现 / 行为符合预期），由 `mai-fix-workflow` 在执行修复时按该方法验证；无法预先确定验证方法的修复项标注"待验证"并给出候选方法。
④ **复杂问题分层（止血 + 长线共存）**：问题复杂时，方案必须分两层：
   - **止血方案**：最小改动、立即生效、缓解用户可见问题（可先上线）
   - **长线方案**：根治性修复或架构改进，可与止血方案共存并逐步替换
   - 长线方案若超出本单范围或需专项跟进：**在门禁全部通过后**（Step 4 阶段），用 `osbot-issue` skill 给特定 owner 开独立 issue 单，写明依赖关系与前置条件（**记得加依赖检查**：确认依赖项/前置 MR/相关单已就绪），并在本单结论中注明跟进 issue 编号。
⑤ **"无法给出结论"时的修复方案区输出规则**：整体结论为"无法给出结论"时，2.10 报告第 8 节修复方案区**只允许两类内容**：
   - **建议性止血项**：不依赖根因定谳的缓解措施（限流/超时/容错/降级等），标注"待根因确认后评估是否保留"；
   - **待办清单**：2.8 后续动作（补日志 / 复现 / QA 复现 / 源码确认）及跟进项。
   **禁止**在无根因时输出"确定修复项"或泛泛修复建议（与 ① 绑定根因要求冲突时以本条为准）。

**2.10 分析报告输出**（落盘：`.claude/ipd-conclusions/<issId>-report[-vN].md`；**base 文件 `<issId>-report.md` 原地更新为最新版**，版本化历史文件保留 `-vN` 后缀）：
```markdown
# IPD 根因分析报告 (<issId>)  [结论版本: vN]
- 日志时间范围 / 分析时间
- 0. 整体结论（二值：确定根因 / 无法给出结论 + 2.8 后续动作）
- 1. 日志概览（文件数/时间跨度/Session 数；**必须含 Android logcat 分析情况：logcat 主缓冲文件路径、是否解压 dumpstate 内层 zip、覆盖时段**）
- 2. 全量事件时间线
- 3. Session 统计与成功/失败对比（Android 端问题必须含 logcat 中成功/失败样本的执行对比）
- 4. 问题定界（主责 + 多端证据链）
- 5. 源码分析（仓库/分支/版本 + 全链路代码↔日志对应表 + 无法闭合环节清单）
- 6. 日志证据 ↔ 源码分析逻辑闭环对照表（2.7 产出，逐环节双向对齐）
- 7. 根因定位（证据链 + 闭合性验证 + 内部环节置信度标注，仅供内部定位薄弱点）
- 8. 修复方案（2.9 产出：每项绑定根因环节 + 修复机制 + 止血/长线分层 + 验证方法）
- 9. 其他发现（潜在问题/性能瓶颈/改进建议；**必须含问题域与贡献度标注：每个发现注明 主问题/强相关/次生/无关 + 贡献度 + 建议 assign 对象**）
- 10. 凭证清单（3.1 规范：实际读取的 file:line + 原文摘录 + 执行操作；**Android 端问题必须含 logcat 凭证条目**）
- 11. 2.8 用户决策记录（若走补日志/复现/源码确认路径：决策人/时间/路径/结果）
```
> Android 端问题：报告第 1 节未说明 logcat 分析情况、第 10 节凭证无 logcat 条目 → 门禁按 2.2b 打回。

### Step 3: 门禁体系（独立子 agent 复核，流水线）

#### 3.0 门禁总览：依赖、执行顺序、串行/并行

门禁是**流水线**：前置门禁的输出是后置门禁的输入，后置门禁必须基于前置门禁的**最新结论**复核。按依赖关系决定串行/并行，无依赖的门禁可并行启动。

| 门禁 | 输入依赖 | 执行顺序 | 并行性 | 审查对象 |
|---|---|---|---|---|
| A1 根因定性复核 | 2.4 源码分析 + 2.5 根因 + 2.10 报告 + 2.7 闭环表 | 第 1 批 | 与 A2 并行 | 根因定性、证据链、结论规范、闭环表、深度分析、降级正确性（2.2b 语义链） |
| A2 日志信息利用率 | 日志目录 + attachmentJson + 2.5 根因结论 | 第 1 批 | 与 A1 并行 | 日志全量利用、logcat 使用率/完备性（唯一归属）、多问题识别、补拉建议、降级正确性 |
| A3 IPD 评论核查 | Step 1 评论 + **A1 通过的结论版本** | 第 2 批（A1 通过后） | 与 A2 并行 | 评论参考、矛盾处理、结论版本绑定 |
| A4 独立对抗性审查 | **A1 与 A2 均通过后的**完整报告 + A3 报告 | 第 3 批 | **串行，A4 之前必须等 A1 与 A2 通过** | 对抗性推翻尝试 + 门禁报告审计 + 凭证对抗核查 |

依赖规则：
- **A1 与 A2 并行启动**（互不依赖；A2 在并行时基于 2.5 根因结论草案核查日志利用，A1 通过后若结论变化按 3.6 重跑）
- **A3 串行在 A1 之后**：A3 核查"评论结论与当前结论版本的矛盾"，必须基于 A1 认可的最新结论版本，**不得在 A1 通过前并行**
- **A4 串行在 A1 与 A2 之后**：对抗对象是双门禁认可的结论
- 任何门禁打回导致前置步骤重跑 → 见 3.6 打回与重算规则

#### 3.0b 定向核验协议（所有门禁复核者强制遵守）

复核者核验证据采用**定向核验**，禁止整读超大文件（防爆上下文、防走形式）：
- **大文件定向检索**：对 100MB 级日志（如 bugreport 主缓冲）用 grep/关键字检索 + 时间窗切片定位，禁止全文顺序读取；引用以 `文件:行号` + 行区间（默认 ±5 行上下文）呈现
- **行号定位**：先 grep 定位目标行号，再读取该行 ±N 行核对上下文，禁止凭记忆或报告转述引用
- **源码核对**：用仓库 grep/glob 定位 `File.kt:line`，核对代码摘录与行号一致
- **记录检索动作**：复核者必须把实际执行的检索命令与命中行号写入门禁报告凭证（供审计重放）

#### 3.1 结论输出规范（所有结论必须满足，门禁据此核查）

任何根因结论（含 IPD 评论、本地留档、门禁报告中的定责）必须同时包含：

1. **关键流程描述**：用户 query → LLM 解析 → 工具调用 → 协议消息 → 对端处理 → 结果回传的完整链路叙述
2. **日志证据**：每条关键事件带 `日志文件:行号` + 原文摘录
3. **源码证据**：每个定责环节带 `源码文件:行号` + 关键代码摘录（来自 2.4）
4. **双向闭环**：日志↔源码闭环对照表（2.7），**存在任何 ❌ 环节 → 整体结论必须为"无法给出结论"**
5. **证据链结构**：现象 → 直接原因 → 深层原因 → 根因，逐跳双重证据
6. **执行时间线明确**：给出端到端时间线（含精确时间戳、双端对应事件、各环节耗时），不得只有结论没有时间过程
7. **深度分析**：每个定责环节必须深挖到"为什么"（代码逻辑 + 运行时行为 + 触发条件），不得停留在"现象描述"或"表面归因"（终止判据见 2.5）
8. **结论整体二值化（强制，禁止模糊）**：整体结论必须二值——要么**确定根因**（全部环节证据链完整闭合、无任何影响定责的不明确处），要么**无法给出结论**（列出全部缺口 + 2.8 的后续动作）；**禁止"可能/疑似/大概率"等模糊定责、禁止"A 环节确定 B 环节待补"的混合定谳、禁止用模糊表述掩盖未确认环节**
9. **依赖溯源**：结论所依赖的前置门禁结论及其版本/轮次（供 3.6 重算判断）
10. **结论版本号**：每版结论必须有唯一版本标识（如 v1/v2/时间戳），门禁判定与重跑都绑定该版本（对应 3.6"通过绑定结论版本"）
11. **凭证清单（强制，防伪造）**：主分析报告与每份门禁报告必须附**凭证清单**——逐条列出"我实际读取/验证过的材料"：
    - 日志：`日志文件:行号` + 该行原文摘录（供他人独立重放核对）
    - 源码：`源码文件:行号` + 代码摘录（供他人打开仓库核对）
    - 操作：执行过的检索/解码/对比动作（grep 关键字、base64 解码、时间戳换算等）及结果
    - **未实际读取/验证的内容不得出现在凭证中，也不得声称验证过**；凭证中任何 file:line 引用必须可被另一独立 agent 重放验证

不满足上述任何一项的结论 = 结论不规范，门禁必须打回。

#### 3.2 门禁 A1 — 根因定性复核

子 agent 审查材料：分析报告 + 日志目录 + 相关代码路径。检查：
- 证据链闭合度：现象→直接原因→深层原因→根因,每一跳是否有日志+代码双重证据、有无逻辑跳跃
- **结论规范核查（强制项，对应 3.1）**：关键流程描述 / 日志证据 file:line / 源码证据 File.kt:line / 闭环表 / 执行时间线 / 深度分析 / 结论整体二值化 / 依赖溯源 / 凭证清单 是否齐全，缺一项即打回
- **凭证可证实性核查（强制项，防伪造，分级处置）**：
  - 报告是否附凭证清单（实际读取的 file:line + 原文摘录 + 执行过的检索/解码操作）
  - **复核者抽查重放（按 3.0b 定向核验协议）**：抽取 ≥1 条凭证中的 file:line 引用，亲自打开日志/源码核对原文；发现可疑引用时增加抽查数量
  - **引用不符分级处置**：
    - 行号轻微偏移 / 摘录不精确（内容实质相符）→ 打回要求修正，不视为伪造
    - 内容实质不符（引用与原文对不上）→ 打回 + 要求重新核实该处
    - 凭空捏造（引用不存在 / 声称读取了未读内容）→ 伪造，严重处理，打回
  - 报告声称"已验证"的内容是否都有对应凭证条目（声称验证但无凭证 → 打回）
- **强制深度分析核查（核心）**：复核者必须对报告每个定责环节做深度分析——
  - 是否深挖到"为什么"（代码逻辑 + 运行时行为 + 触发条件），且符合 2.5 终止判据（不因无限深挖而卡死，也不停留在表面）
  - 报告中对每个环节的解释是否经得起逐行推敲（代码分支、条件判定、数据流）
  - 复核者自己必须重读关键源码片段与日志原文验证，**不得仅凭报告转述就认可**
- **执行时间线核查（强制项）**：报告是否给出端到端时间线（精确时间戳、双端对应、各环节耗时）；时间线是否与日志原文逐点一致；时间线是否完整覆盖问题全过程（无跳过时段）
- **降级正确性校验（强制项，对应 2.2b 语义链，A1 侧：定责语义）**：附件缺 logcat（或未覆盖时段）时——
  - 闭环对照表是否**将受影响的 Android 执行环节独立入表并标 ❌**（而非省略该环节）；
  - 闭环表存在 ❌ 时整体结论是否已正确降级为"无法给出结论"（或已走 2.8 决策路径）；
  - **若附件缺 logcat 却仍维持"确定根因"（且受影响环节参与定责、无 logcat 之外反证）→ 打回**；
  - "⚠️ 日志完备性警告"是否在报告显著位置显式声明（**缺警告即打回**）
  - （logcat 实际使用率/完备性的深度回扫核查**归属 A2 单方负责**，见 3.3；A1 不再重复核查日志利用）
- **结论整体二值化核查（强制项）**：
  - 结论必须是"确定根因"或"无法给出结论"二选一，出现"可能/疑似/大概率/推测"等模糊表述 → 打回要求明确化
  - 出现"A 环节确定、B 环节待补"的混合定谳 → **打回**（整体性结论强制）
  - 判定为"确定根因"：全部环节证据链是否完整闭合、是否有任何影响定责的不明确处（任一影响定责的不明确 → 不得判确定）
  - 判定为"无法给出结论"：是否明确列出全部缺口与 2.8 后续动作（不得以模糊话术掩盖）
- **源码分析充分性（强制项）**：
  - 是否对双端全链路源码逐一分析（发起端工具参数构造 / 协议载荷 / 接收端 prompt 拼接 / 执行与回传），只分析单侧即视为不充分
  - 是否给出 `源码文件:行号` + 代码摘录 + 日志对应证据的完整对应表
  - 是否确认了仓库路径 / 模块 / 分支 / 版本（无法确认时是否向用户询问 / 走 2.8 路径 D）
  - 有无"仅凭日志推断、无源码支撑"的定责（此类必须打回）
- **日志↔源码逻辑闭环核查（强制项，对应 2.7）**：
  - 报告是否包含逐环节"日志证据 file:line ↔ 源码证据 File.kt:line"双向闭环对照表
  - 每个关键环节是否双向闭合（日志有行为痕迹、源码有实现点，且逻辑一致）
  - 存在 ❌ 未闭合环节时整体结论是否已降级为"无法给出结论"（未降级即打回）
  - 日志与源码矛盾是否被定位并解释（版本不匹配/分支差异），未解释即打回
- 标记"证据不足却下结论"处

输出落盘 `.claude/ipd-conclusions/<issId>-review-A1.md`：逐项检查 + **凭证抽查结果** + 替代假设列表 + 闭合度评分 + 结论（通过/打回+修改点清单）。

#### 3.3 门禁 A2 — 日志信息利用率审查

子 agent 审查材料：日志目录 + 分析报告 + attachmentJson 清单 + 2.5 根因结论。检查：
- **根因结论的日志支撑充分性**：2.5 根因结论的每一个定责环节，在日志中是否有充分、直接的证据；有无"结论需要某条日志佐证但报告中缺失"的环节
- **日志全量利用复核**：是否漏掉其他 session/事件/成功样本（对照时间线与日志原文逐段回扫，尤其问题发生前后的空档期）
- **Android logcat 使用核查（强制项，对应 2.2b，Android 端问题必查）**：
  - **是否解压并分析了 bugreport 内层 dumpstate zip 的 `bugreport-*.txt`（adb logcat 主缓冲）**——仅看 app 级 debug_log 视为未完成 logcat 分析
  - **日志完备性警告核查**：附件缺少 logcat 或 logcat 未覆盖问题时段时，报告是否给出"⚠️ 日志完备性警告"并说明受影响的环节——缺警告即打回
  - **降级正确性校验（强制项）**：附件缺 logcat 时，结论是否因受影响环节未闭合而正确降级为"无法给出结论"（闭环表 ❌ + 2.5 硬约束，或走 2.8 决策路径）；**未降级却维持"确定根因" → 打回**（不得以"已有警告"为由维持确定——警告是提醒项，不豁免闭环 ❌ 的降级后果）
  - **logcat 覆盖核查**：问题时段内关键 Android 执行（worker 动作/服务进程启动/工具调用/检索/回传）在 logcat 中是否有对应记录；**关键执行环节 logcat 零命中且报告未解释 → 打回**
  - **日志使用率复核（覆盖 logcat 与其他重要日志）**：复核所有重要日志（系统级 logcat、app 级 debug_log、服务/进程日志、PC 端日志等）的使用情况；Android 端问题凭证中 logcat 条目应覆盖问题时段关键执行链；**logcat 使用率不足（关键环节缺失 logcat 证据）→ 整体打回，不得以"缺日志"降级为无法给出结论（除非真实回扫 logcat 确认无记录）**
  - 复核者按 3.0b 定向核验协议回扫 bugreport 内层 logcat 主缓冲的问题时段（grep + 时间窗切片），验证"未触发/未执行/无记录"类断言的真实性
- **主要原因遗漏检查**：日志中出现的异常/失败/重试/冲突/边界行为，是否都被纳入分析或明确解释过无关性；**有无日志已提示但报告忽略的"更主要原因"**
- **深度分析强制**：A2 复核者必须按 3.0b 定向核验协议亲自回读关键日志时段（不得仅依赖报告引用），验证每条引用与原文一致、无截断取巧
- **凭证抽查（强制，分级处置）**：抽取 ≥1 条报告中的日志引用，亲自打开日志核对原文与行号；发现可疑时增加抽查；行号轻微偏移/摘录不精确 → 要求修正，凭空捏造 → 伪造打回
- 一份日志分析出了几个问题？是否有多个独立根因？
- 日志确实不足以支撑结论时：**不执行自动补拉**，按 2.8 用户决策流程处理

输出落盘 `.claude/ipd-conclusions/<issId>-review-A2.md`：日志利用清单（逐环节对照）+ 遗漏/忽略清单 + 凭证抽查结果 + 结论（通过/打回+缺口清单）。

#### 3.4 门禁 A3 — IPD 评论核查（串行在 A1 通过后）

子 agent 审查材料：问题单全部评论（Step 1 拉取）+ **A1 通过的最新结论版本**（报告）。检查：
- 自己的评论、其他人的评论是否都参考过？关键信息（测试步骤/复现条件/历史分析尝试）是否纳入？
- 评论结论与本次分析结论版本的矛盾点是否已处理？
- 凭证要求：A3 报告中引用的每条评论（内容/作者/时间）必须与 Step 1 拉取的评论原文一致，附对应评论条目凭证

输出落盘 `.claude/ipd-conclusions/<issId>-review-A3.md`：评论核查清单（每条状态）+ 矛盾处理 + 结论（绑定其核查的结论版本）。

#### 3.5 门禁 A4 — 独立对抗性审查（强制，串行在 A1 与 A2 通过后）

子 agent 审查材料：A1 与 A2 均通过后的完整报告 + 日志目录 + 源码路径 + 已通过的 A1/A2/A3 审查报告。**立场：试图推翻**。

针对**分析过程**：
- 时间线是否被篡改/美化/选择性截取？是否存在与结论相悖但未报告的日志行？
- 源码引用是否真实存在（行号、代码摘录与仓库实际一致）？是否张冠李戴（引用了无关模块/错误分支/其他版本）？
- 闭环表是否存在"假闭合"（日志与源码表面对齐但语义不符）？
- **凭证对抗核查（强制，分级处置）**：按 3.0b 定向核验协议复核主报告与 A1/A2/A3 报告的凭证清单，抽取 ≥5 条 file:line 亲自重放核对（发现可疑时增加）；行号偏移/摘录不精确 → 要求修正，凭空捏造 → 伪造打回

针对**结论**：
- 提出 ≥3 个对抗性替代根因（含最不利假设），逐一验证原结论能否排除
- 结论是否超出现有证据强度（如把"强相关"说成"因果"、把"无法给出结论"说成"已定谳"）？
- 与 A1/A2/A3 已认可结论是否有未消化的矛盾？

**门禁报告审计（A4 独有职责）**：审计 A1/A2/A3 报告本身是否走形式（抽查其"无需重跑/复核通过"的自判是否有依据），发现走形式 → 打回对应门禁重跑；**无关分类抽查（4.6⑥）**：抽查被归为"无关/低贡献"的现象是否确实与根因无关（对照日志/源码判断），发现错误分类 → 打回重新分类。

输出落盘 `.claude/ipd-conclusions/<issId>-review-A4.md`：对抗假设列表 + 攻击点核查 + 凭证对抗结果 + 门禁报告审计 + 结论（维持通过 / 打回+证据缺口清单）。

#### 3.6 打回与重算规则（流水线语义）

**核心不变量：门禁的"通过"绑定特定结论版本，不是永久有效。**

- 每次门禁判定都基于**当时的结论版本**（报告 + 闭环表 + 依赖溯源中的版本号/轮次）
- 结论被**任何**门禁打回并更新后，**该新结论版本上的所有此前判定（无论通过与否、门禁先后）全部失效**，必须用新结论重新判定
- 单一流水线内不保留"旧结论上通过"的豁免；只有用户显式豁免可豁免重跑（记录原因）

**打回（任意门禁均可触发）**：
- 任一门禁不认可结论 → 打回并指明重跑目标（对应前置步骤或前置门禁）
- **任意门禁不认可任意前置门禁**：后置门禁发现前置门禁审查有遗漏/错误 → 可打回该前置门禁重跑，不受顺序限制
- **证据不足**：允许打回**更前置的步骤**（如 A1 认为源码不足 → 打回 2.4；A2 认为日志不足 → 按 2.8 用户决策流程处理；A4 认为需补实验 → 打回 Step 2 重分析），不限于相邻环节

**收敛机制（防 A1↔A2 乒乓死锁）**：
- 同一结论版本上，**连续互打 ≥2 轮**（如 A1↔A2 相互打回两次）→ **升级用户仲裁**（向用户说明双方分歧，由用户裁决）；仲裁**设时限**（默认 1 个工作日，可在汇报时与用户约定），**超时未裁决 → 默认按"无法给出结论 + 缺口清单"收尾**，不阻塞流程
- **打回计数强制落盘（可审计）**：每次打回必须追加记录到 `.claude/ipd-conclusions/<issId>-rejections.md`（版本号 + 打回门禁 + 打回原因 + 时间），作为收敛判断的唯一审计依据
- **总打回轮次上限 3 轮（按本次分析会话累计，跨版本）**：同一分析会话内（v1→v2→v3 全部版本合计）被门禁打回累计 ≥3 次仍未通过 → 停止流水线，结论定为"无法给出结论 + 缺口清单"，向用户说明。**跨版本 churn（v1→v1.1→v1.2…）不豁免该上限**；继续推进必须是用户显式豁免（记录豁免原因与累计轮次）或用户明确要求重跑
- 用户豁免可跳过收敛限制（记录原因）

**结论变更后的重跑判定（所有门禁，含已通过者）**：

一旦主 agent 因任何打回更新了结论（定性变化 / 补充证据 / 闭环表变化），**每个门禁必须基于最新结论版本独立判定自己是否需要重跑**，判定结果只可能是三种之一：

| 判定 | 适用情形 | 动作 |
|---|---|---|
| **必须重跑** | 结论变更影响了该门禁的审查对象（几乎所有情况：A1 审的就是结论，A2 审日志对结论的支撑，A3 审结论与评论矛盾，A4 对抗新结论） | 用新结论完整重跑，产出新审查报告 |
| **无需重跑（注明复核）** | 结论变更与该门禁审查对象**确无交集**（如 A3 中某条与根因定性无关的评论核查条目） | 不重跑，但须在新报告中注明"已基于最新结论复核，无影响" |
| **复核通过（更新版本）** | 受影响但用新结论复核后结论未变、判定仍成立 | 更新审查报告版本号并注明"复核通过" |

**典型场景**：
- A1/A2 并行通过（v1 结论）→ A3 打回 → 主 agent 更新定性（v2 结论）
- → **A1 必须用 v2 结论重跑**（A1 审的就是结论，v1 通过不代表 v2 通过）
- → **A2 用 v2 结论重跑**（日志对 v2 结论的支撑需重新核）
- → A3 用 v2 结论重跑（打回发起者）
- → A4 尚未跑，直接基于 v2 结论执行
- 任何门禁若在 v1 上标记过"通过"，在 v2 上该标记无效

**流水线终止条件**：最新结论版本上，A1 通过 → A2 通过（可与 A1 并行）→ A3 通过（A1 后）→ A4 对抗性审查通过 → 门禁完成，进入 Step 4。任一打回 → 修正后按依赖重跑对应环节，直至在**同一结论版本**上全部通过（或用户显式豁免并记录原因，或达 3.6 收敛上限）。

### Step 4: 结论上传与留档

门禁体系全过（A1/A2 并行通过，A3 通过，A4 对抗性审查通过；或用户豁免并记录）后：

**4.1 本地留档** `.claude/ipd-conclusions/<issId>-conclusion.md`（版本化文件名规范见 2.10）：
```markdown
# IPD 分析结论 <issId>  [结论版本: vN]
- 整体结论（二值：确定根因 / 无法给出结论 + 2.8 后续动作）
- 根因证据链（日志+代码 file:line，代码证据必须来自 2.4 源码分析）
- 源码分析记录（仓库/分支/版本 + 全链路代码↔日志对应表 + 无法闭合环节）
- 日志↔源码闭环对照表（2.7 产出，逐环节双向对齐，含 ❌ 缺口清单）
- 关键流程描述（用户 query → LLM → 工具 → 协议 → 对端 → 回传 完整链路）
- 执行时间线（端到端）
- 问题定界（主责）
- 问题清单（本日志分析出的全部问题，可能多个根因）
- **问题域与贡献度（4.6 产出）**：每个问题标注 主问题/强相关/次生/无关 + 贡献度(高/中/低/无关) + 建议 assign 对象(模块维护人)
- 修复方案（2.9：每项绑定根因环节 + 修复机制 + 止血/长线分层 + 验证方法 + 跟进 issue）
- 凭证清单（3.1 规范：实际读取的 file:line + 原文摘录 + 执行操作）
- 2.8 用户决策记录（若走补日志/复现/源码确认路径：决策人/时间/路径/结果）
- 审查记录: A1 ✓(评分) / A2 ✓ / A3 ✓ / A4 ✓（或豁免原因），各门禁基于的结论版本
- 依赖溯源: 本结论基于的 前置门禁结论版本/轮次（供重算判断）
- 关联文件: 分析报告（`<issId>-report[-vN].md`）/ 审查报告（`<issId>-review-A{1..4}[-vN].md`）路径
```

**4.2 更新修复数据库**：
```bash
python <WF_ROOT>/fix-db.py update <issId> --status conclusion_uploaded -f conclusion="<一句话根因>" -t "根因定谳上传 IPD"
```

**4.3 上传根因评论到 IPD**（`M_saveComment`，单个 text 节点内嵌 HTML）：
```
【根因定谳 + 分析结论】整体结论(二值：确定根因 / 无法给出结论+后续动作) / 关键流程描述(用户 query → LLM → 工具 → 协议 → 对端 → 回传) /
执行时间线(端到端) / 根因实证(日志证据 file:line + 源码证据 File.kt:line) / 问题定界(主责 + 问题域/贡献度) /
问题清单(全部问题 + 建议 assign 对象) / 修复方案(绑定根因 + 止血/长线分层 + 验证方法 + 跟进 issue) / 审查通过记录(含 A4 对抗性审查)
```
HTML 格式要点：整个分析作为单个 text 节点、`<p>` 分段、`<br>` 换行、`<b>` 粗体、`<code>` 代码。
> **强制**：评论中的根因定责必须有源码证据支撑（File.kt:line），仅日志推断的定责禁止写入评论；**整体结论二值化（确定根因 / 无法给出结论），禁止模糊表述、禁止部分定谳**；证据不足时按 2.8 标注"无法给出结论 + 已申请补日志/要求 QA 复现/待源码确认"，**不进入定谳上传**；评论须包含关键流程描述与执行时间线（3.1 规范）。**内部置信度标注（实证/推断/猜测）不进入 IPD 评论。**

**4.4 告知用户**：结论已上传 + 本地留档路径 + 可进入 `mai-fix-workflow` 开始修复。

**4.5 结论收敛后复核（强制，不可省略）**：

> 结论定谳并上传后，**必须复核三件事**，确认结论正确落地，缺一即视为流程未完成：

① **复核 IPD 单落地**：用 `M_getCommentList` / `M_pageOverallComment` **实查**该单评论，确认根因结论已上传（评论 id、内容、作者、时间与上传一致）；评论未落单或内容不符 → 重新上传并复查
② **复核 fix-db 更新**：`python <WF_ROOT>/fix-db.py query <issId>` 实查，确认 status=`conclusion_uploaded`、conclusion 字段为最终定谳内容、timeline 含本次记录；未更新 → 补执行 4.2
③ **复核本地留档**：确认 `.claude/ipd-conclusions/<issId>-conclusion.md` 存在且为**最新版本**（若有 `-vN` 版本文件，校验最新 vN 与 base 文件内容一致；含整体结论/证据链/审查记录）

**4.6 问题域与贡献度分析（强制，防过度发散）**：

> 分析过程中识别出的**全部问题**，必须按问题域分类并评估对 IPD 问题的贡献度，**不得无差别深挖发散**，也不得遗漏高贡献问题。

① **问题域分类**：对日志/源码中识别出的每个独立问题，归入：
   - **主问题**：直接对应 IPD 单描述的现象/根因——必须分析清楚（含直接原因/深层原因/根因，证据链闭合）
   - **强相关问题**：与 IPD 问题在同一链路/同一模块/同一根因上，贡献度高——必须分析清楚
   - **次生问题**：由主问题引发或伴随出现（如并发任务、链路过期缺陷），对 IPD 问题有贡献但非主因——评估贡献度，高贡献纳入结论，低贡献归"其他问题"
   - **不相关问题**：日志中其他独立现象（非本单范围）——写明"其他问题"，不深挖
② **贡献度评估**：每个问题标注对 IPD 问题的贡献度——**高**（直接导致现象）/ **中**（显著影响/放大）/ **低**（伴随但不影响结论）/ **无关**（独立现象）
③ **assign 对象建议**：贡献度 **高/中** 的问题，**通过 git 定位模块维护人**（`git log --format='%an' -- <模块路径>` 统计最近提交者、codeowner/OWNERS 文件等），在结论与 IPD 评论中给出"**建议 assign 对象**"（模块维护人）；无法定位时标注"维护人待确认"
④ **其他问题记录**：贡献度 **低/无关** 的问题，写明"**其他问题**"并**评估影响**（是否影响用户体验/稳定性/性能/安全）；**影响大的也必须记录**（纳入结论"其他发现"或开跟进 issue），影响小的简述即可
⑤ **多根因场景**：IPD 单可能包含多个独立根因——每个根因独立成问题域，分别分析贡献度与 assign 对象，结论中并列呈现
⑥ **无关分类抽查（防"其他问题"滥用）**：被归为"无关/低贡献"的现象，主 agent 自查 + A4 审计抽查（对照日志/源码判断其确实与根因无关）；**不得把未闭合/未深挖的主问题或强相关环节塞入"其他问题"以保护整体"确定根因"**；发现错误分类 → 打回重新分类
⑦ **组合规则（与 2.5 衔接）**：整体二值化只针对主问题与强相关问题；"其他问题"（低/无关贡献）单独列出、评估影响，**不阻塞**整体定谳

**2.10 报告模板**（见上）第 9 节"其他发现"即承载问题域分类与贡献度结论；第 4 节"问题定界"必须包含主问题/强相关问题/次生问题的贡献度标注。

## 与 mai-fix-workflow 的关系

`mai-fix-workflow`（修复）**强制要求**本 skill 的完整结论（IPD 评论 + 本地文件双查），无结论拒绝开始。因此本 skill 必须完成 Step 3 门禁体系（A1/A2/A3/A4）全部审查 + Step 4 上传留档。**且结论中的修复方案必须按 2.9 绑定根因、写明验证方法（修复执行与验证由 mai-fix-workflow 完成），作为其执行依据。**

## 错误处理

- **IPD 查询失败**: `setup.py check` / mai-env-doctor 定位 MCP 问题,重试一次
- **日志下载失败**: 检查 fdsId 有效性,逐个重试
- **源码路径/分支/版本不确定**: 按 2.8 路径 D——向用户询问确认并设时限（默认 1 个工作日）；超时未确认 → 结论"无法给出结论（待源码确认）"+ 待办清单，不阻塞流程收尾
- **日志/证据不足（无法闭合）**: **不自动补拉**，按 2.8 用户决策流程（汇报用户 → 补 IPD 评论申请日志 / 自行复现 / 要求 QA 复现），记录决策人/时间/路径
- **审查打回**: 按审查报告修改后重新提交,不豁免则必须通过；结论版本变化 → 所有门禁按 3.6 用新版本重新判定；每次打回记入 `<issId>-rejections.md`；连续互打 ≥2 轮或总打回 ≥3 轮（按会话累计）→ 按 3.6 收敛机制升级用户仲裁（超时默认收尾）/停止
- **上传失败**: 检查 M_saveComment 参数（单个 text 节点内嵌 HTML）,重试
